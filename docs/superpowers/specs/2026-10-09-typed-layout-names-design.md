# Typed Layout Names (`dts` option)

## Context

`LayoutName` is `string | false` (`src/runtime/layoutMeta.ts`). A typo in
`definePage({ meta: { layout: 'dashbord' } })` or `setPageLayout('typo')`
type-checks and only shows up at runtime, where the page silently renders
`fallbackLayout`. Editors cannot autocomplete layout names either.

Nuxt solves this by generating a type file from the discovered layouts
(`packages/nuxt/src/pages/module.ts`):

```ts
declare module 'nuxt/app' {
  interface NuxtLayouts {
    'default': ComponentProps<typeof import('.../default.vue')>
  }
  export type LayoutKey = keyof NuxtLayouts extends never ? string : keyof NuxtLayouts
  interface PageMeta { layout?: MaybeRef<LayoutKey | false> | /* { name, props } */ }
}
```

This spec brings the same mechanism to this plugin: a registry interface keyed
by normalized layout name, augmented by a generated `.d.ts`, with a fallback to
`string` when nothing is registered.

## Goals

- Layout names are type-checked and autocompleted in `meta.layout` (string and
  `{ name, props }` forms, including inside `definePage`), `setPageLayout` and
  `useLayout`.
- Works in both plugin mode and client-side mode.
- Opt-in via a new `dts` option; without it, types are exactly as today
  (`LayoutName` is `string | false`).
- Registry shape is forward-compatible with per-layout props typing.
- Ship as a minor release (`3.3.0`).

## Non-Goals

- Per-layout props typing (`props` inferred from the layout component). The
  registry value is `unknown` so this can be added later by changing the value
  to `ComponentProps<typeof import(...)>` without changing the registry shape.
- Typing `defaultLayout` / `fallbackLayout` in `vite.config`. The `.d.ts` is
  generated from that config, so typing the config with it is circular. Wrong
  names there are already handled at runtime by `fallbackLayout`.
- A build-time warning when `defaultLayout` does not exist.
- Enabling `dts` by default (candidate for v4).
- `Ref` / `ComputedRef` values for `meta.layout` (a runtime feature Nuxt has).
- Editing the user's `tsconfig.json`.

## Public API

### Option

Added to both `UserOptions` (`Layouts()`) and `clientSideOptions`
(`ClientSideLayout()`):

```ts
/**
 * Generate a `.d.ts` that types layout names.
 * `true` writes `layouts.d.ts` in the Vite root; a string is a path relative to the root.
 * @default false
 */
dts?: boolean | string
```

`canEnableClientLayout` accepts `dts` as an isomorphic key, so
`Layouts({ layoutsDirs: 'src/layouts', dts: true })` still returns the
client-side plugin.

### Types (`vite-plugin-vue-layouts-next/runtime`)

```ts
/** Augmented by the generated `.d.ts`; keys are normalized layout names. */
export interface LayoutRegistry {}

type RegisteredLayoutName = keyof LayoutRegistry extends never
  ? string
  : keyof LayoutRegistry & string

export type LayoutName = RegisteredLayoutName | false
/** Nuxt-compatible alias: a layout name without `false`. */
export type LayoutKey = Exclude<LayoutName, false>
```

`LayoutRegistry` and `LayoutKey` are exported from `src/runtime/index.ts`.
Everything that already uses `LayoutName` picks up the narrowed type with no
further change: `RouteMeta.layout`, `LayoutOptions.name`, `setPageLayout`,
`useLayout`, and the declarations in `client.d.ts`. `LayoutMap` stays
`Record<string, ...>` and runtime code is unchanged, since a registered name is
a subtype of `string`.

### Generated file

For layouts `default.vue`, `admin.vue`, `sub/layoutSub.vue`:

```ts
/* eslint-disable */
/* prettier-ignore */
// Generated by vite-plugin-vue-layouts-next. Do not edit.
export {}

declare module 'vite-plugin-vue-layouts-next/runtime' {
  interface LayoutRegistry {
    "admin": unknown
    "default": unknown
    "sub-layout-sub": unknown
  }
}
```

- Names come from `normalizeLayoutName`, the same function the runtime uses.
- Names are sorted and de-duplicated so the output is stable across runs and
  machines (no git noise).
- Keys are emitted with `JSON.stringify`.
- The lint/format-disable header matches what `unplugin-vue-router` puts in
  `typed-router.d.ts`, so a generated file in the user's project does not fail
  their ESLint/Prettier run (antfu's config would reject the double quotes).
- With no layouts, the interface is emitted empty and `LayoutName` falls back
  to `string | false`.

## Implementation

### `src/dts.ts` (new)

- `resolveDtsPath(dts: boolean | string | undefined, root: string): string | undefined`
  — `undefined` when disabled, `<root>/layouts.d.ts` for `true`, otherwise
  `resolve(root, dts)`.
- `createDtsCode(names: string[]): string` — pure; sorts, de-duplicates and
  renders the file above.
- `writeDts(path: string, code: string): Promise<void>` — creates the parent
  directory if needed and writes only when the content differs from what is on
  disk, so `tsc --watch` and Vite's watcher are not triggered for nothing.

### Plugin mode (`Layout()` in `src/index.ts`)

- `configResolved` resolves the dts path from `config.root`.
- The layout file scan in `load` is extracted into a helper that returns the
  `FileContainer[]`. `load` keeps using it for the virtual module only; it does
  not write the `.d.ts` (`buildStart` and the watcher already cover every case).
- `buildStart` also runs the scan + write when `dts` is enabled, so the file
  exists after `vite build` and before the virtual module is first requested in
  dev.
- In `configureServer`, `add` and `unlink` events inside a layouts directory
  regenerate the file. `change` does not (names cannot change).

### Client-side mode (`ClientSideLayout()`)

The virtual module uses `import.meta.glob`, so nothing is scanned in Node.
When `dts` is enabled only:

- `configResolved` stores the root and resolves the layouts dir and dts path.
- `buildStart` scans `<layoutDir>/**/*.vue` with `fast-glob` (same pattern the
  glob uses), normalizes names with `normalizeLayoutName` and writes the file.
- `configureServer` watches the layouts dir and regenerates on `add` / `unlink`.

With `dts` disabled, the client-side plugin behaves exactly as today.

### Ordering

In both modes, every regeneration (scan + write) runs through one queue per
plugin instance (`serialize()` in `src/dts.ts`). Overlapping `add`/`unlink`
events, for example from a `git checkout`, would otherwise let an earlier scan
finish last and overwrite the file with a stale list.

### Edge cases

| Case | Behavior |
|---|---|
| Same name in several `layoutsDirs` | Emitted once. Runtime keeps last-wins. |
| Empty layouts directory | Empty interface; types fall back to `string`. |
| Name only known at runtime (e.g. from an API) | `setPageLayout(name as LayoutName)`; documented. |
| Write fails (read-only FS) | Log a warning through Vite's logger; do not fail the build. |

## Testing

### Behavior (Vitest, node environment)

- `test/dts.test.ts`
  - `createDtsCode`: sorted, de-duplicated, empty input gives an empty
    interface, keys quoted; inline snapshot of a full file.
  - `resolveDtsPath`: disabled, `true`, relative string.
  - `writeDts`: creates the file and missing parent directory; skips the write
    when content is unchanged.
- Plugin tests, using `test/fixtures/layouts` and a temp output directory:
  - Plugin mode: `configResolved` + `buildStart` writes a file containing every
    fixture layout name.
  - Client-side mode: same assertion.
  - No `dts` option: no file is written.
  - `Layout({ layoutsDirs: 'src/layouts', dts: true })` returns the client-side
    plugin.
  - Watcher: `add` / `unlink` regenerate the file, `change` does not.

### Types (`tsc` + `expectTypeOf`)

- Type tests are `test/types/**/*.test-d.ts` files using `expectTypeOf` from
  Vitest and `@ts-expect-error`, compiled by `tsc` (not executed). Vitest's
  typecheck mode runs one tsconfig per project, and these cases need two, so
  `pnpm typecheck` (already run in CI) is extended to
  `tsc && tsc -p test/types/registry && tsc -p test/types/fallback`, and the
  root `tsconfig.json` excludes `test/types`.
- Augmentation is global to a TS program, so the two cases use separate
  tsconfigs, each mapping `vite-plugin-vue-layouts-next/runtime` to
  `src/runtime/index.ts` via `paths`:
  - `test/types/registry/` — includes a fixture `.d.ts` registering `default`
    and `admin`. Asserts `LayoutName` is `'default' | 'admin' | false`,
    `LayoutKey` is `'default' | 'admin'`, `setPageLayout('typo')` and
    `RouteMeta` `layout: 'typo'` / `{ name: 'typo' }` are errors
    (`@ts-expect-error`), valid names pass.
  - `test/types/fallback/` — no augmentation. Asserts `LayoutName` is
    `string | false`, which locks in backward compatibility.
